# 失败分析与走不通的尝试

记录“试过但没用”的东西，比只贴成功结果更有信息量——它界定了方法的边界。

---

## 1. 失败模式分类（30 轮 + 15 轮真机统计）

| 形态（脚本自动判定） | 占比 | 现场观察 | 主要对策 |
|---|---|---|---|
| 下探 + 回位 | 33 % → 73 %* | 伸下去、回到初始位 | —— |
| 只下探没回位 | 57 % → 20 %* | 伸到一半/在积木上方停住 | 加时长、缩短重规划间隔、多训练 |
| 几乎没动 | 10 % → 7 %* | 起始姿态就偏，或该轮没录上 | 检查 repo-id 与起始位姿 |

\* 前一组是“10 秒 + 动作块 100 步盲执行”，后一组是“20 秒 + 每 10 步重规划”。

**关键结论**：演示数据本身很干净（50 条末帧几乎都能看到积木在纸盒里），
所以瓶颈不在数据质量，而在**训练量**与**执行策略**。

## 2. 时序集成（temporal ensembling）在本任务上更差

ACT 论文常用 `temporal_ensemble_coeff = 0.01`，思路是每一步都重新预测，并对重叠动作块做指数加权平均。

- 开启方式（注意必须用 `+` 新增键，因为 checkpoint 的 config 里只有旧字段名 `temporal_ensemble_momentum`）：

  ```powershell
  --policy-overrides "+policy.temporal_ensemble_coeff=0.01" "policy.n_action_steps=1"
  ```

- 实测：**10 轮 0 成功**，且比不开更差。原因：加权平均把动作**抹平变慢**，
  8–10 秒的预算里根本走不完“接近→夹住→抬起→入盒”。
- 结论：本任务动作是“分段、有明显快慢节奏”的抓放，**平均会破坏节奏**；
  更适合的替代是“缩短重规划间隔”（`n_action_steps=10`），保留原始的快速段，实测成功率翻倍。

## 3. 自动判定“积木是否进盒”踩了三次坑

想脱离人工目视，尝试过三种自动判据，都失败：

| 方法 | 失败原因 |
|---|---|
| 红色连通域质心追踪 | 画面左侧的**红色线束**也被识别，初始位置满屏乱跳，面积变化出现 12×/32× 的异常 |
| 加形状约束（圆度 > 0.55、长宽比 0.45–2.2） | 积木靠近镜头时变成大面积斜四边形，被面积上限/圆度阈值过滤掉 → 近距离漏检 |
| 固定桌面 ROI 统计红色像素 | 俯视相机装在臂上（随臂移动），积木的像素位置/大小随姿态变化，ROI 假设不成立 |

**最终做法**：用 `scripts/summarize_eval.py` 导出“末帧接触表”（每轮取末帧拼成一张图），
人工一眼扫过；动作形态（下探/回位）交给数值判定。**自动化判定留给固定外置相机 + 目标检测模型**，
这也是下一步要做的事。

> 上面三种方法的第一版代码保留在 [../perception/](../perception/)：颜色阈值检测、像素/厘米标定、
> 质心轨迹都在里面，可以直接拿来复现这些失败，也能作为“改用检测模型”的对照基线。

## 4. 其它“看着像模型问题、其实是配置问题”的坑

| 现象 | 真实原因 |
|---|---|
| 机械臂完全不动，但相机窗口弹出来了 | 复用同一个 `--repo-id` → `--num-episodes` 是**累计集数**，第二次启动立刻退出，只跑 warmup |
| 每帧都 `Failed to read/write ... Motor 'N'`，循环 2 Hz | leader 臂配了 `0xAA` 帧的 `GBotMotorsBus`，硬件是 `0xFF` 帧的 STS3215 |
| 进程无 traceback 直接消失，CPU 跑满 | OpenCV MSMF 后端打开相机时的静默崩溃（28 s/次） |
| 抓不到但“动作幅度很小” | 实际是 `episode-time-s` 太短，策略还没走到抓取阶段就被截断 |
| 模型明明会动，但轨迹来回修正 | `n_action_steps=100` 一次执行 3.3 秒不重新观察，误差累积 |

## 5. 尚未尝试但值得做的

- **标定精度量化**：重复定位精度（回同一点 n=30 的标准差）、手眼标定重投影误差。
- **数据规模曲线**：10 / 25 / 50 条演示 → 成功率，用来判断“加数据”和“加步数”哪个更划算。
- **端侧部署**：ONNX/TensorRT + INT8，功耗-延迟曲线（当前 4060 上单次推理 2.3 ms，模型 51.6 M，
  fp32 197 MiB → INT8 约 49 MiB，非常适合边缘设备）。
